🔄 Iterate after deployment

The cycle never stops — feedback → improvement → deploy → repeat

🎯 Deploy isn't the end

The first version always has bugs, confusing UX, and missing features. That's normal — and it's exactly where Claude Code shines most: iterate quickly. What would take days of manual refactoring, Claude handles in minutes.

Each iteration moves you up a level. Consistency over time > a single launch sprint.

✓ Healthy iteration

  • ✓Small, frequent commits (every day or week)
  • ✓Open issues to track upcoming improvements
  • ✓Feedback from real users guides priorities
  • ✓Claude Code implements improvements in minutes

✗ Abandoned project

  • ✗Last commit 6+ months ago
  • ✗Open issues with no response
  • ✗Outdated dependencies with vulnerabilities
  • ✗README outdated compared to the current code

🏷️ Releases and tags

Formal versions — communicate progress to users and recruiters

1

Create a tag and release via gh CLI

# Criar tag local e push
$ git tag v1.0.0
$ git push origin v1.0.0

# Criar release no GitHub com notas automáticas
$ gh release create v1.0.0 \
  --title "v1.0.0 — Lançamento inicial" \
  --generate-notes

# Listar releases
$ gh release list

# Ver release específica
$ gh release view v1.0.0
2

Versioning convention (SemVer)

v1.0.0 → First stable version, public API defined

v1.1.0 → New feature compatible with the previous version

v1.1.1 → Bug fix, with no behavior change

v2.0.0 → Breaking change — API changed

💡 --generate-notes is gold

O gh release create --generate-notes automatically reads the PR and commit history since the last release and generates a formatted changelog. No manual effort—perfect for maintaining consistency.

📚 Document well

Your future self will thank you — and so will recruiters

Documentation is what turns a repository into a project. Without it, even you will be asking yourself in 3 months, "How does this thing work again?"

✓ Minimal documentation

  • ✓README with installation and basic usage instructions
  • ✓CHANGELOG.md with version history
  • ✓Comments in non-obvious functions
  • ✓LICENSE (MIT for open source projects)

📈 Advanced documentation

  • →CONTRIBUTING.md to attract contributors
  • →ADR (Architecture Decision Records)
  • →GitHub Wiki for long-form docs
  • →Docusaurus for large projects

🤖 Claude automatically documents code

Ask: "Add JSDoc comments to all functions in this file" or "Generate the CONTRIBUTING.md explaining how to set up the environment and open PRs". Claude reads the code and generates accurate, consistent documentation.

♻️ Keep the project alive

Consistency > intensity—the secret to projects that last

🌿 Living project vs. archived project

A living project doesn’t need marathon sprints. It needs consistency: one small improvement per week is more valuable than 3 months of silence followed by a major update. Recruiters look at the contribution graph.

🤖

Dependabot — automatic updates

Activates automatically on GitHub. Creates PRs to update dependencies with vulnerabilities. Configure it in .github/dependabot.yml:

version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
🌱

Good First Issues — attracting contributors

Issues marked with good first issue appear in GitHub search results for people looking to contribute for the first time. A great way to grow the community.

$ gh issue create \
  --title "Melhorar mensagem de erro do login" \
  --label "good first issue"

✓ Weekly maintenance ritual

  • ✓Review open issues (respond or close)
  • ✓Merge approved Dependabot PRs
  • ✓At least 1 small improvement commit
  • ✓Update README if anything changed

📦 When to archive

  • →Project replaced by something better
  • →Outdated technology without maintenance
  • →Use Settings → Archive repository to flag
  • →Let the README explain why
