🔄 Iterar después del deploy

El ciclo nunca se detiene: feedback → mejora → deploy → se repite

🎯 El deploy no es el final

La primera versión siempre tiene bugs, una UX confusa y funcionalidades faltantes. Es normal — y es justamente ahí donde Claude Code más se destaca: iterar con rapidez. Lo que llevaría días de refactorización manual, Claude lo resuelve en minutos.

Cada iteración sube un peldaño. La consistencia a lo largo del tiempo > un sprint único de lanzamiento.

✓ Iteración saludable

  • ✓Commits pequeños y frecuentes (todos los días o cada semana)
  • ✓Issues abiertas para dar seguimiento a próximas mejoras
  • ✓La retroalimentación de usuarios reales guía las prioridades
  • ✓Claude Code implementa mejoras en minutos

✗ Proyecto abandonado

  • ✗Último commit hace más de 6 meses
  • ✗Issues abiertas sin respuesta
  • ✗Dependencias desactualizadas con vulnerabilidades
  • ✗README desactualizado respecto del código actual

🏷️ Releases y tags

Versiones formales — comunicar la evolución a usuarios y reclutadores

1

Crear una tag y un release mediante gh CLI

# Criar tag local e push
$ git tag v1.0.0
$ git push origin v1.0.0

# Criar release no GitHub com notas automáticas
$ gh release create v1.0.0 \
  --title "v1.0.0 — Lançamento inicial" \
  --generate-notes

# Listar releases
$ gh release list

# Ver release específica
$ gh release view v1.0.0
2

Convención de versiones (SemVer)

v1.0.0 → Primera versión estable, API pública definida

v1.1.0 → Nueva feature compatible con la versión anterior

v1.1.1 → Corrección de bug, sin cambios de comportamiento

v2.0.0 → Breaking change — la API cambió

💡 --generate-notes es oro

O gh release create --generate-notes lee automáticamente el historial de PR y commits desde la última release y genera un changelog con formato. Sin esfuerzo manual: perfecto para mantener la coherencia.

Tus proyectos como escaparate: qué es lo que realmente miran los reclutadores

🐙 GitHub Profile README

Crea el repo especial usuario/usuario con un README.md. Aparece en tu perfil de GitHub como página personalizada.

$ gh repo create usuario --public

Repo usuario.github.io se convierte en tu sitio personal. Claude Code puede generar la página completa con tarjetas de tus proyectos.

📚 Documentar bien

Tu yo del futuro te lo agradecerá — y los reclutadores también

La documentación es lo que convierte un repositorio en un proyecto. Sin ella, hasta tú mismo dentro de 3 meses te preguntarás "¿cómo funciona esto?"

✓ Documentación mínima

  • ✓README con instrucciones de instalación y uso básico
  • ✓CHANGELOG.md con historial de versiones
  • ✓Comentarios en funciones no obvias
  • ✓LICENSE (MIT para proyectos abiertos)

📈 Documentación avanzada

  • →CONTRIBUTING.md para atraer colaboradores
  • →ADR (Architecture Decision Records)
  • →Wiki de GitHub para documentación extensa
  • →Docusaurus para proyectos grandes

🤖 Claude documenta el código automáticamente

Pide: "Agrega comentarios JSDoc a todas las funciones de este archivo" o "Genera el CONTRIBUTING.md explicando cómo configurar el entorno y abrir PRs". Claude lee el código y genera documentación precisa y coherente.

📢 Pedir comentarios y difundir

Crear una audiencia para el proyecto — feedback real > suposiciones

1

Comunidades para difundir

✓ Reddit: r/webdev, r/programming
✓ Dev.to (artículo + enlace)
✓ Twitter/X con #buildinpublic
✓ Show HN (Hacker News)
✓ LinkedIn (publicación técnica)
✓ Product Hunt (lanzamiento)
2

Pedir feedback estructurado

GitHub Discussions es ideal para recibir comentarios de forma asíncrona. Las Issues con la etiqueta "feedback" o "question" dejan claro que quieres escuchar a los usuarios.

$ gh issue create \
  --title "[FEEDBACK] O que você achou?" \
  --label feedback \
  --body "Conte o que funcionou e o que falta"

✓ Funciona hacer público el proceso

  • ✓Compartir el proceso atrae audiencia antes del lanzamiento
  • ✓La retroalimentación temprana evita construir lo equivocado
  • ✓Los registros de progreso se convierten en un portafolio de aprendizaje

✗ Errores comunes

  • ✗Esperar a que esté «perfecto» para divulgarlo — nunca llega
  • ✗Ignorar a los primeros usuarios (son oro)
  • ✗Difundir sin un enlace directo para probar

♻️ Mantener vivo el proyecto

Consistencia > intensidad: el secreto de los proyectos que perduran

🌿 Proyecto activo vs. proyecto archivado

Un proyecto vivo no necesita sprints maratónicos. Necesita consistencia: una pequeña mejora por semana vale más que 3 meses de silencio seguidos de una gran actualización. Los reclutadores ven el contribution graph.

🤖

Dependabot — actualización automática

Se activa automáticamente en GitHub. Crea PRs para actualizar dependencias con vulnerabilidades. Configúralo en .github/dependabot.yml:

version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
🌱

Good First Issues — atraer colaboradores

Issues marcadas con good first issue aparecen en las búsquedas de GitHub para quienes quieren contribuir por primera vez. Una excelente forma de hacer crecer la comunidad.

$ gh issue create \
  --title "Melhorar mensagem de erro do login" \
  --label "good first issue"

✓ Ritual de mantenimiento semanal

  • ✓Revisar issues abiertas (responder o cerrar)
  • ✓Fusionar los PR de Dependabot aprobados
  • ✓Al menos 1 commit de mejora pequeña
  • ✓Actualizar README si algo cambió

📦 Cuándo archivar

  • →Proyecto reemplazado por algo mejor
  • →Tecnología obsoleta sin mantenimiento
  • →Usa Settings → Archive repository para señalar
  • →Deja que el README explique el motivo
